# Code Sherpas Software Development Standards

Principles, patterns and conventions for developing software at Code Sherpas. Each file is one standard, self-contained, and normative: it states what the code must look like and how to review it.

## How to consume these standards

Repositories reference these files from their `AGENTS.md` / `CLAUDE.md` by URL. There is no versioning: consumers always read `main`, so a merge here reaches every repository in its next session.

```
https://raw.githubusercontent.com/code-sherpas/software-development-standards/main/<standard>.md
```

## How to wire this into a repository

A consuming repository carries a section in its `AGENTS.md` that tells the agent to read the index at session start, and in full every standard that applies to its work. That section has one canonical copy here: [setup/agents-md-section.md](setup/agents-md-section.md). Copy it verbatim; do not adapt it per repository.

**Current section version: 3**

At session start an agent reads this index anyway, so it compares that number against the version stated at the end of its own copy at no extra cost. When they differ, the copy in the repository is stale and the agent says so instead of silently working from outdated instructions.

## Automated checks

Some standards are backed by a script that the agent runtime runs at a given moment, such as the end of a turn. **A check belongs to the standard it backs**: it lives at `checks/<standard>/<check>.sh`, the standard names it, and [checks/checks.tsv](checks/checks.tsv) says on which event it runs. A runner, such as the `base` plugin of [code-sherpas/claude-code-plugins](https://github.com/code-sherpas/claude-code-plugins) for Claude Code, knows nothing but this repository. It reads `checks.tsv` from `main` and downloads the scripts it names, keeping the last copy it got for when it cannot reach GitHub, and then runs them. A merge here reaches every session's next check, the same way it reaches every session's next read.

A check script:

- reads the runtime's hook input on stdin (for Claude Code, the JSON with `session_id`);
- prints nothing when it finds nothing. When it finds something, it prints one message for the agent: what it found and what the agent has to decide. It does not restate the rule or link it. **The runner puts the standard's name and link in front of every finding**, taken from `checks.tsv`, so the agent always has the whole rule at hand and no check can forget it;
- exits 0 whenever it ran. A non-zero exit means the check itself failed: the runner reports that failure and does not stop the agent;
- does not decide what happens to the agent. Whether a finding stops the turn, and that it stops it only once, is the runner's job.

`checks/checks.test.ts` keeps the manifest, the scripts and the standards consistent: nothing listed is missing, nothing present is unlisted, and no standard names a check that is gone. Each check has its own test next to it, `<check>.test.ts`, and that is checked too.

## Contributing

`main` changes only through the merge queue: `gh pr merge <n>` puts a pull request in it, and the queue's build of the tree that will land must pass `quality_checks`. A push to a pull request runs nothing, so a green pull request means nothing has been checked yet. The tests run on Linux and macOS, the systems the checks run on: `node --test 'checks/**/*.test.ts' 'evals/**/*.test.ts'` (Node 24 or later). A change that adds a standard or changes its «What Counts as» section must update, in the same change, its entry in the index below and its cases in [evals/index](evals/index/README.md); the queue checks it with `node evals/index/scope-changes.ts <base>`.

## Index (61 standards)

Read in full every standard whose entry applies to any part of your work: what you write, change, move, review, run or ship. That includes the ones that apply to almost every change. Reading one too many costs only tokens; missing one lets its rule be broken unseen.

### Domain model

- [Domain Entity](domain-entity.md) — Define a domain entity as a domain object with a unique identity that persists over time, even as its attributes change.
- [Domain Entity Aggregate Boundaries](aggregate-boundaries.md) — When a domain entity relates to another domain entity, determine whether they belong to the same aggregate or to different aggregates, apply the correct reference style, and persist the boundary decision so it is available to future tasks.
- [Domain Entity Reference Direction](domain-entity-reference-direction.md) — When two domain entities are related, determine whether each entity needs a reference to the other based on its own domain responsibilities — invariants and behavior — not on read or query convenience.
- [Domain Entity Reference Optionality](domain-entity-reference-optionality.md) — When a domain entity holds a reference to another domain entity, determine whether that reference is required or optional based on whether the entity can exist in a valid domain state without it.
- [Domain Entity Typed IDs](domain-entity-typed-ids.md) — Choose the right level of type distinction for domain entity identifiers based on whether the project's type system is nominal or structural.
- [Domain Entity UUIDv4 IDs](domain-entity-uuidv4-ids.md) — Applies wherever a domain entity's id is defined, created, parsed, validated, serialized or mapped to persistence, transport or another application, a request or message schema that checks an id included: represent domain entity identifiers with UUIDv4.
- [Immutable Domain Entities](immutable-domain-entities.md) — Applies whenever a domain entity is written or changed, a renamed field included: apply the immutable design pattern.
- [Domain Service](domain-service.md) — When domain logic involves multiple aggregates and does not naturally belong to any single one of them, encapsulate that logic in a domain service; logic that a single aggregate can own goes on that aggregate, never in a service.

### Business logic

When a change writes, changes, moves or reviews a business-logic entry point — a command or query handler, a use case, an application service, a server action, a job or a route that holds business rules — every entry-point standard below applies whose own condition holds: Typical Domain-Entity Entry Points, the «… for Business Logic Entry Points» standards and the three «Ensure …» standards.

- [Bounded Context Layout](bounded-context-layout.md) — Source is organized by business context first and by layer second: domain, application, primary-adapter and secondary-adapter inside each context, with `domain` present when there is one, nothing outside a context reaching into its adapters, and `shared` treated as where coupling hides.
- [Dependency Direction](dependency-direction.md) — Business logic declares the interfaces it needs and infrastructure implements them from outside: the interface belongs to the caller rather than mirroring a vendor's API, the clock and the id generator are dependencies too, and adapters at the edge translate and delegate rather than decide.
- [Business Logic](business-logic.md) — Applies to any code that applies a business rule, decision or workflow, wherever it lives, adapters, routes and jobs included. Define business logic as the rules, algorithms, and workflows in software that govern how data is created, stored, and transformed so real business policies become automated actions.
- [Typical Domain-Entity Entry Points for Business Logic](business-logic-typical-domain-entity-entry-points.md) — Applies whenever a business-logic entry point around a domain entity is written, changed, moved or reviewed: it is one of a standard set — create, edit, find by id, search, delete, change a finite state, associate, check whether an action is allowed — instead of an ad hoc operation.
- [One Entry Point per Module for Business Logic](business-logic-entry-point-one-per-module.md) — Every business-logic entry point must be a separate module.
- [Prefer Top-Level Functions for Business Logic Entry Points](business-logic-entry-point-prefer-top-level-functions.md) — When implementing a business-logic entry point, prefer a top-level function over a class or object, as long as the project stack allows it without introducing friction.
- [Command-Query Separation for Business Logic Entry Points](business-logic-entry-point-command-query-separation.md) — Apply Command-Query Separation at entry points to business logic.
- [CQS Handler Signatures for Business Logic Entry Points](business-logic-entry-point-cqs-handler-signatures.md) — Apply a consistent signature pattern to business-logic entry points when Command-Query Separation is already the governing design rule.
- [Colocate Types with Business Logic Entry Points](business-logic-entry-point-colocate-types.md) — When a business-logic entry point has parameters or return values whose types are declared by the project, those types must live in the same file as the entry point, as long as the project stack allows it.
- [Primitive Input Types for Business Logic Entry Points](business-logic-entry-point-primitive-input-types.md) — The fields of command and query types accepted by business-logic entry points must use only primitive or basic types.
- [Domain Entity Payload Types for Business Logic Entry Points](business-logic-entry-point-domain-entity-payload-types.md) — When a business-logic entry point returns domain-entity data, the payload type must be the domain-entity type itself.
- [Ensure Business Constraints for Business Logic](business-logic-ensure-business-constraints.md) — Write business-logic business constraints with a consistent `ensure ...` formalism translated into the syntax and naming conventions of the language in use.
- [Ensure Authenticated Requester for Business Logic Entry Points](business-logic-ensure-authenticated-requester.md) — Every business-logic entry point that requires authentication must include an `ensure requester is authenticated` business constraint as the first check before any other business logic runs.
- [Ensure Authorized Requester for Business Logic Entry Points](business-logic-ensure-authorized-requester.md) — Every business-logic entry point that requires authorization must include an `ensure requester is authorized` business constraint, placed after authentication and before any business operation runs.
- [Execution Context for Business Logic Entry Points](business-logic-entry-point-execution-context.md) — Every business-logic entry point must set up an execution context that makes request-scoped data implicitly accessible from any point in the execution chain.
- [Database Transaction for Business Logic Entry Points](business-logic-entry-point-database-transaction.md) — Every business-logic entry point that interacts with a database must wrap its entire flow in a single database transaction, when the underlying persistence technology supports transactions.
- [Transaction Isolation Levels for Business Logic Entry Points](business-logic-entry-point-transaction-isolation-levels.md) — When a business-logic entry point wraps its flow in a database transaction and follows Command-Query Separation, set the transaction isolation level based on whether the entry point is a command handler or a query handler, when the underlying persistence technology supports configurable isolation levels.
- [Use Repositories in Business Logic Entry Points](business-logic-entry-point-use-repositories.md) — Every business-logic entry point that persists, retrieves, or deletes domain entities must do so exclusively through repositories.
- [Repository Interface for Business Logic Entry Points](business-logic-entry-point-repository-interface.md) — Business-logic entry points must depend on a repository interface — not on the concrete repository implementation.
- [Repository Domain Types for Business Logic Entry Points](business-logic-entry-point-repository-domain-types.md) — The types exchanged between business-logic entry points and repositories must be domain-entity types and domain value types.
- [Repository Operations for Business Logic Entry Points](business-logic-entry-point-repository-operations.md) — Repository interfaces must expose a standard set of operations with clear naming, explicit intent, predictable return types, and a strict error model.

### Persistence

- [Repository No Business Logic](repository-no-business-logic.md) — Repositories must contain no business logic.
- [Write Persistence Representations](write-persistence-representations.md) — Write or update the persistence representation that maps application data to the storage technology in use.

### Types, errors and style

- [Built-In Temporal Types](built-in-temporal-types.md) — Applies to any code that defines, creates, parses, stores, sends or converts a date or time, also one that only passes through a message, a row or an API. Represent temporal values with built-in or standard-library temporal types that match their real meaning, and tell instants from civil times: a wall-clock time a person chose in a place is stored as a local date-time plus a canonical IANA zone, with the instant derived from it.
- [UTC Zoned Temporal Types](utc-zoned-temporal-types.md) — Applies wherever an instant is defined, parsed, serialized, stored or converted, also when it only crosses a boundary as text. Instants — what happened, or must happen at an absolute moment — use timezone-aware built-in types set to UTC; civil times a person chose in a place are out of scope.
- [ISO 8601 Millisecond Precision](iso8601-millisecond-precision.md) — Applies wherever a date or time is written as text or read from text: JSON, messages, query strings, logs a program parses, documentation of a contract. When a temporal value must be represented textually, use ISO 8601.
- [Neverthrow Return Types](neverthrow-return-types.md) — Applies to every function or method a change writes or changes, a one-line edit included, and to judging existing code: model every compatible one with `neverthrow` return types in TypeScript or JavaScript, and with the stack's established typed result in any other — Rust or Swift `Result`, Scala or Arrow `Either`, Go's `(value, error)`.
- [Neverthrow Exception Wrapping](neverthrow-wrap-exceptions.md) — Applies wherever a recoverable failure enters code as a thrown exception or a rejected promise, in any stack: capture it at its source with `neverthrow` helpers in TypeScript or JavaScript, or the stack's equivalent elsewhere, instead of ad hoc `try/catch`.
- [Prefer Named Functions Over Anonymous Functions](prefer-named-functions.md) — Applies to any change that defines a function, inline callbacks, handlers, mappers, lambdas and test callbacks included: prefer a named function over an anonymous one, in any stack, within the idioms the standard allows.
- [Failure Reporting](failure-reporting.md) — A component fails whenever it cannot do its job, always; reporting that failure to observability is a separate decision, and it belongs to whoever knows the context, because the same error is an incident for one caller and an expected outcome for another.
- [Serialization Boundaries](serialization-boundaries.md) — What crosses a boundary loses the jurisdiction of the tools that enforced its guarantees, so design what crosses to keep naming the domain, rebuild the type on arrival through one door, and handle both ways a remote call fails.

### User interface

When a change touches an interface, the business logic an interface exposes — a rule, a permission, a precondition, a lifecycle, even with no screen in the change — or settles what an interface will do, Business Logic and Interface Coherence, Unambiguous States and No Dead Ends apply together.

- [Accessibility](accessibility.md) — Every interface shipped is accessible, targeting WCAG 2.2 Level AA: native semantics before ARIA, full keyboard operation, visible and unobscured focus, contrast and reflow, announced dynamic changes, and the criteria WCAG 2.2 added for dragging, target size, redundant entry and accessible authentication.
- [Internationalization](internationalization.md) — Applies to any change that produces or changes text a person reads, amounts, dates and statuses derived from data included; log lines and developer output are exempt. Every string a person reads is localized in every supported locale: the locales are one list everything else derives from, keys are typed so a missing one does not compile, each concept has one catalogue and one resolver, the database stores keys rather than display text, and sentences are whole messages rather than concatenated fragments.
- [Business Logic and Interface Coherence](business-logic-interface-coherence.md) — Applies to any change to an interface a person operates, or to business logic one exposes — a rule, a limit, a state machine, a permission, an error it returns — to settling it while refining or splitting, and to judging an existing area: the interface offers exactly what the logic allows in each state, states every constraint before submitting, turns every outcome into a message in domain language, shows each fact as the logic computes it, uses the domain's words and states, and gets what it needs by extending the logic, never by working around it.
- [Unambiguous States](unambiguous-states.md) — Applies to any change to what an interface shows in any of its states, or to a lifecycle, background process or time rule a person sees, to settling it while refining or splitting, and to judging an existing area: every reachable combination of lifecycle, data, request, role, time and device is designed, different situations never look the same, progress, staleness and partial outcomes are visible, empty areas say why and how to fill them, and the person always knows where they are.
- [No Dead Ends](no-dead-ends.md) — Applies to any change to an interface or a flow, and to any backend change that writes a lifecycle, a permission, a precondition or a deletion rule a person meets, even with no screen in it, to settling it while refining or splitting, and to judging an existing area: every goal can be completed inside the product, every state has a way out, every refusal says why and who can change it, mistakes can be corrected, prerequisites lead to where they are made, every capability is in the navigation, and repetitive work scales.
- [Design System Adoption](design-system-adoption.md) — Applies, in a product whose project names a design system, to any change to its interface, to migrating an interface onto it, and to judging an existing area: the design system's components, tokens and patterns are used whenever it has them, what it lacks is taken to its owners as a problem, it wins conflicts with the product's habits, and adopting it keeps the business logic, changing its public interface only through the logic.
- [State-Coherent Prototypes](state-coherent-prototypes.md) — A prototype that stands in for a product behaves like it: every interaction, path and state works, everything shown derives from one state and stays coherent across screens, roles and device modes, what cannot be clicked is simulated and marked as outside the design, and it meets the same generic UI/UX and accessibility baseline as the product, verified with scenario scripts, random exploration and checks in every viewport.

### Testing

- [Automated Testing](automated-testing.md) — Applies to any test written, reviewed or repaired, at any level, and to any change whose work includes checking it with tests or scripts. Where the testing rules live, starting with what makes a test worth having: it fails when the behaviour it describes breaks and not otherwise, it asserts what a caller can observe rather than how the subject is built, it never asserts on a double, and each double names the situation instead of restating how it is assembled.
- [Model-Interpreted Features](model-interpreted-features.md) — When a model interprets what the user asked, the feature ships a corpus and the corpus is the test suite: one table crossing the shapes an object can take with the kinds of request that stress it, split across unit tests that gate CI, a thin e2e subset, and an evaluation harness run by hand that names what it missed.

### Planning work

- [Auditing a Product Area](auditing-a-product-area.md) — When asked to audit an existing part of a product, or whether it is ready for a use it has not had, establish with evidence how far it meets every standard that applies — the code standards included: domain model, entry points, persistence, error model, layout — not only the interface ones: delimit the area, audit several areas one at a time in dependency order, build an inventory of entities, entry points, screens, roles, states and goals, observe in production without changing anything and provoke the rest locally, and record each finding — what happens, how to reproduce it, its consequence and the rule it breaks, never a solution — in one task that refining decides on.
- [Refining Work](refining-work.md) — Before work is split or built, the request becomes one task in the project's task tracker that settles what will be done and why: facts come through sub-agents from the documentation, checked against the code when the task rests on them, the interview asks one question at a time until none is open, terms and decisions go in the task while the product documentation waits for what reaches production, the draft is confirmed once, and the next phase starts in a new session from the task alone.
- [Creating Tasks](creating-tasks.md) — Applies whenever a task, subtask, defect, finding or increment is created in a project's task tracker, by any flow — refining, auditing, fixing an error, splitting, or a problem noticed along the way — and not to editing a task that exists: search the tracker first for the same work, an equivalent one or a broader task that should include it, extend that task instead of creating another, ask before changing what it had agreed, and say what was found.
- [Splitting Work into Increments](splitting-work-into-increments.md) — A refined task is split into the smallest increments of functionality usable in production, each delivering named user stories, tied by the tracker's blocking relation into a graph, with an order and a feature-flag strategy; the code is read through sub-agents and corrects the task where it proves it wrong, each increment carries only what shipping it needs, the parent task keeps only the plan and the state, and the plan is confirmed once before anything is created.

### Shipping changes

- [Shipping Increments](shipping-increments.md) — A split task is shipped one increment at a time, each built, reviewed, merged, deployed and verified in production before anything that depends on it starts: the session's agent coordinates and talks to the person, a new builder per increment, a different reviewer before the change request, a verifier after the deploy, every one reading the standards index and choosing what it reads in full; questions and merges go to the person, and the run takes how many increments to ship at most and how many in parallel.
- [Pre-Merge Gates](pre-merge-gates.md) — Before a change enters the main branch, six gates must hold: the change is ready to merge, its pre-merge plan was run by whoever integrates it, it was exercised by hand, any data migration was run against a representative dataset, any data it leaves behind ships the mechanism that removes it, and any entry point it adds or changes was called as someone who must be refused.
- [Post-Deploy Verification](post-deploy-verification.md) — Applies to every change that reaches production, by any route, and to whoever builds it, reviews its plan or verifies it; only documentation, tooling configuration, test-only changes and changes fully covered by a check that runs against production are exempt. A change is done only once it has been used in production the way its real consumers use it — a person through the interface, another application through its contract, an agent through its path — on a deploy confirmed to carry it, with dedicated test accounts, and when it fails the person is told with the evidence and decides whether to revert.
- [Stacked Changes](stacked-changes.md) — Stack a change only on a change it depends on, whatever the platform calls it — a pull request, a merge request: no global stack, one stack per line of work, every layer validated against the stack's base, merge the lowest ready layer one at a time, and a group lands only when all of it is verified and it is one change in production.
- [Expand-Contract Schema Changes](expand-contract-schema-changes.md) — Applies to any change to what is stored — a migration, a new table or column, a renamed field, a queue message's shape — additive ones included: each is classified as destructive or not, and reported. During a deploy two versions run against the same storage, so a change that removes, renames or narrows anything stored is split across deploys — expand, migrate, contract — the contract step names the deploy that removed the last reader, and the repository enforces it with an automated check.

### Operations

- [Fixing Reported Errors](fixing-reported-errors.md) — When an error is reported, first find out whether it is already resolved; if not, gather every fact the system holds, find its duplicates, reproduce it, and decide whether it is the application's error, the user's — whose report is removed and whose repetition is made less likely, never by making it the application's — or neither; record it as a defect task written in domain language, with root cause, reporting point, the layer that owns the fix and sourced evidence, and ask before starting the fix; then fix it at that layer with its regression test, and close the task only once the deploy is live and the error has stayed quiet.

### Working with other agents

- [Collaborating Across Agent Sessions](collaborating-across-agent-sessions.md) — When an agent is blocked by, or has a question about, work another agent session owns, it looks for a fix already in flight, finds the owning session and writes it a message that stands on its own, treats what it hears as information rather than permission, settles between sessions what is theirs to settle, and brings the person in only for what they cannot settle — with the diagnosis and the options ready.
- [Leave Nothing Running](leave-nothing-running.md) — Applies whenever an agent's work starts something that keeps running — exercising or reproducing a change in the running application, running tests against a database or containers they bring up, a development server, a browser, a background job, a tunnel — fixing, building, splitting, verifying and auditing included. When an agent hands control back, everything it started that is still running is decided on: stopped because nothing needs it, or kept on purpose and said so; it knows what is its own by mechanism, not by appearance, checks that what it stopped is gone, never stops what it did not start without the person's permission, and is backed by an automated check wherever the agent runtime allows one.

### Integration

- [Integration Logic](integration-logic.md) — Applies to any code that talks to another application, and a database is one: repositories, ORM queries and mappings, schemas and migrations, HTTP clients, webhooks, queue producers and consumers. Define integration logic as the code required for two independent applications to communicate.
